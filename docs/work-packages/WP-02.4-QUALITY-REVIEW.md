## Source → counterexample → correction

### I2 — condition identity

Legacy `conditionIds` are definition IDs, while `ApplyCare.conditionId` addresses an instance. Treating a loaded definition ID as a condition instance would make two wounds indistinguishable and invent source/onset information. `CompanyPhysicalState.conditions` is therefore instance-backed. `materializeCompanyPhysicalState` requires explicit instance/source/onset bindings for every non-empty legacy occurrence; the lifecycle list is only the derived capability view.

### I1 — one indivisible draft

Giving physical handlers their own commit/revision would allow money to settle while an item/care mutation fails. `prepareCompanyEconomy` materializes and validates one root, executes lifecycle, finance and physical changes together, and publishes only the existing lifecycle canonical/public revisions.

### Corrected profile 0.2 and causal time

A delayed death learned after advancing to the current tick could otherwise consume food and perform recovery for time after the actual death. Retroactive `RecordDeath` and dead `ResolveMissing` apply the causal correction first, rebuild the corrected food requirements, then run food/recovery. The active profile remains minor 50 ticks, severe stable 250 ticks after real care, full-health rest basis 100, stamina rest basis 10, and explicit critical window 250 where supplied by the causal source.

### Capacity and mandatory departure return

Reusing ordinary transfer for departure could make a valid dismissal impossible when company storage is full, or tempt deletion of equipment. Ordinary `TransferItem` rejects atomically on capacity. `PHYSICAL_DEPARTURE` creates a local `GROUND_BUNDLE` only for the mandatory company-item return and preserves item IDs and owners.

### Current pools versus maxima and equipment

Equipping healthy gear or applying wound care must not normalize character HP or item condition. Vitals, item condition, equipment and care are separate state. Equip changes slots only; care records/consumes care only; repair changes item condition only; health changes only through eligible recovery.

### Real care and food exactly once

A client receipt ID, repeated care request, or missing provider/stock must not create free treatment or food. Trusted physical evidence is scoped by world/company/revision/tick/source/version/subject. Source effects are idempotent; stock/provider access and payment are checked before mutation; exact fractional food carry is stored.

### Actual versus known

Capture, hidden death, item seizure or food use must not leak through public revision, inventory projection, spendable cash or retry errors. Actual physical state and `physical.knowledge` remain separate. Public revision compares only public economy/lifecycle/physical projections. Observation is the explicit reconciliation point.

### Release versus service membership

Releasing a captive and immediately paying wages would conflate physical availability with duty resumption. Capture/missing pause actual service without ending membership. Release restores physical availability but leaves actual service paused until the existing `ReturnToService` transition.

### Trusted external values

Mutating an evidence object after `prepareCompanyEconomy` must not retroactively mutate saved state or source identity. Finance and physical facts are cloned at admission; stored owners, locations and observation snapshots are owned copies or canonical request keys.

### C04 and QR14-01…05

Simplifying the root around physical execution must not regress backed reservations, public revision or source fan-out. Existing finance allocation/knowledge/payment code remains the owner; physical integration reuses it and keeps command-ID conflict → scoped source replay → fresh revision ordering.
