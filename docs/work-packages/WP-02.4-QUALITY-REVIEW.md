## Source → counterexample → correction

| Source / invariant | Counterexample reviewed | Correction in this implementation |
| --- | --- | --- |
| I2: legacy `conditionIds` are definition IDs; `ApplyCare.conditionId` addresses an instance | Treating a loaded definition ID as a condition instance would make two wounds indistinguishable and would invent source/onset information | `CompanyPhysicalState.conditions` is instance-backed. `materializeCompanyPhysicalState` requires explicit instance/source/onset bindings for every non-empty legacy occurrence; the lifecycle list is only the derived capability view |
| I1: one lifecycle+finance+physical draft and one observable revision | Giving physical handlers their own commit/revision would allow money to settle while an item/care mutation fails | `prepareCompanyEconomy` materializes and validates one root, executes all three components, and publishes only the existing lifecycle canonical/public revisions |
| Corrected profile 0.2: minor 50, stable severe 250 after care, HP 100, stamina 10, critical deadline 250 | A delayed death learned after advancing to the current tick could consume food and perform recovery for time after the actual death | Retroactive `RecordDeath` / dead `ResolveMissing` apply the causal correction first, rebuild the corrected food requirements, then run food/recovery |
| Ordinary capacity is hard; mandatory departure return must not delete property | Reusing ordinary transfer for departure makes an immobile/full-storage dismissal impossible or deletes equipment | Ordinary `TransferItem` rejects atomically on capacity. `PHYSICAL_DEPARTURE` creates a local `GROUND_BUNDLE` only for the mandatory company-item return and preserves item IDs/owners |
| Equip/max condition must not heal or repair | Equipping healthy gear or applying wound care could accidentally normalize character HP or item condition | Vitals, item condition, equipment and care are separate state. Equip changes slots only; care records/consumes care only; repair changes item condition only; health changes only through recovery |
| Care/food are real, exactly-once fulfillment | A client receipt ID, repeated care request, or missing provider/stock could create free treatment/food | Trusted physical evidence is scoped by world/company/revision/tick/source/version/subject. Source effects are idempotent; stock/provider access and payment are checked before mutation; exact fractional food carry is stored |
| Actual and known are different facts | Capture, hidden death, item seizure or food use could leak through public revision, inventory projection, spendable cash or retry errors | Actual physical state and `physical.knowledge` are separate. Public revision compares only public economy/lifecycle/physical projections. Observation is the explicit reconciliation point |
| Release/custody is not service membership | Releasing a captive and immediately paying wages would conflate physical availability with duty resumption | Capture/missing pause actual service without ending membership. Release restores physical availability but leaves actual service paused until the existing `ReturnToService` transition |
| I3: adapter data belongs to the snapshot | Mutating an evidence object after `prepareCompanyEconomy` could retroactively mutate saved state or source identity | Finance and physical facts are cloned at admission; stored owners, locations and observation snapshots are owned copies or canonical request keys |
| C04 and QR14-01…05 remain regression contracts | Simplifying the root around physical execution could regress backed reservations, public revision or source fan-out | Existing finance allocation/knowledge/payment code remains the owner; physical integration reuses it and keeps command-id conflict → scoped source replay → fresh revision ordering |
