## A — API compatibility, not a new product decision

E1: consume actual OPENING_ASSETS, RECRUIT_SETTLEMENT, DUTY_SETTLEMENT and
LEADERSHIP_SETTLEMENT from the existing lifecycle preparer. Missing recipient,
wage terms and local source bindings require finite trusted adapter evidence.
Return a single lifecycle+finance draft. No supplied `settled=true` can complete it.

E2: Wallet owns cash; a funding pool only identifies the actual local purse and
access scope. Reservations reduce spendable cash, never create a second balance.

E3: existing command schema 2 already rejects a DEFAULT subset/payee and requires
a TARGETED payee. Preserve that registry. New execution rejects zero amounts and
overpayment rather than creating advances, gifts or no-op success.

E4: separate actual earned claims from last-known estimates and backed pending
allocations. Unfunded estimates are not money. Hidden fate cannot release a
reservation or redirect colleagues' visible payments.
