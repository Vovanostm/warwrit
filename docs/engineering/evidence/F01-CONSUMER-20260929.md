# F01 trusted-deed nickname consumer

This packet implements existing `ProposeNickname` and `ResolveNickname` lifecycle
commands. It consumes a trusted internal significant-deed fact; it does not
produce that fact or establish the finite cultural nickname catalogue. Full F01
and its producer-to-consent acceptance remain open.

## Contract and behavior

Accepted Q-CHAR-14A (`rec8hgsJFhQb3uqgb`), lifecycle
`recv6d4GVHYW7Q0i4` and acceptance `recGSsmv6BbvenLi4` were read in full from the
September 29 source refresh. Their existing requirements remain: immutable birth
name, culturally appropriate system proposal, player consent, one active nickname
and retained source/reason history. No free-text naming or gameplay bonus is added.

The consumer binds character, birth culture, source, deed kind, reason and text
key. Source replay and command replay use the existing lifecycle receipt owner.
Only an explicitly source-authorized observation reveals a proposal or history;
a generic character-status observation preserves prior nickname knowledge. Player
consent immediately closes that observer's offer and updates accepted identity.
Public records are detached from the retained canonical knowledge.

Optional additive V1 fields preserve old states with no nickname records. Resolved
proposals retain accepted/rejected history, while each character has one active
nickname. The later H unknown-state reader must explicitly accept these optional
fields and preserve their source/reason/time values; it must not silently discard
them. No released migration or combat replay changes in this packet.
