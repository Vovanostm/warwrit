# Quickstart — проверка завершения M1

Руководство задаёт проверяемые сценарии. Их фактическое выполнение в этом
планировании — NOT_RUN. Источники границ — [контракты](contracts/README.md),
сущности и версии — [data-model](data-model.md).

## 1. Предпосылки и выбор задачи

T001 фиксирует checkout и выбранную базу, T003 — write set и владельцев ресурсов.
T002 устанавливает аккаунт, компанию, мир и происхождение сохранения.
Используется реальная доступная компания либо разрешённый естественно созданный
N01 fallback с явным происхождением. Точный критерий находится у владельца задачи.

```bash
cd /Users/vovanostm/learn/warwrit
node --version
pnpm --version
.specify/scripts/bash/check-prerequisites.sh --json --require-spec
```

Ожидается Node 24.20.x, pnpm 11.25.x и активный дизайн-пакет 002 с plan.md.
[Каноническая очередь](tasks.md) владеет T001–T037.
Её пути можно проверить отдельным вызовом с явным выбором каталога.

```bash
SPECIFY_FEATURE_DIRECTORY=/Users/vovanostm/learn/warwrit/specs/002-m1-completion .specify/scripts/bash/check-prerequisites.sh --json --require-spec --require-tasks --include-tasks
```

Перед тестами, использующими workspace exports, обновить соответствующий dist.


Это существующие адресные регрессии. Новый setup/config требует соответствующих

Исторические двухсторонние примеры проверяют собственную совместимость.
Все команды выполняются последовательно, результат отмечает число реально выполненных сценариев.

## 3. Обычный редактор и бой

После реализации выбранной ветки запустить временный стенд на свободных
портах, принадлежащих этому сеансу.

```bash
COMBAT_API_PORT=3022 COMBAT_WEB_PORT=5320 pnpm dev:combat
```

Открыть `http://127.0.0.1:5320/combat-lab`.
Скрипт поднимает локальные in-memory сессии и завершается по Ctrl+C.
Проверка долговременных кампанийных последствий выполняется следующим разделом.

| Шаг | Действие                                                                                                              | Результат                                                                 |
| --- | --------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------- |
| 1   | Создать конфигурации двух и трёх сторон, включая 12×12×12                                                             | Отряды игрока до 6, стороны до 12, всего до 36, управление своим составом |
| 2   | Сохранить/открыть, экспортировать/импортировать конфиг                                                                | Все стороны, unit IDs, позиции, зоны отхода и группы сохранены            |
| 3   | Попытаться запустить 7 бойцов в отряде игрока, 13 на стороне, 4 стороны, повторную принадлежность и совпавшие позиции | Понятный отказ с сохранением исходного состояния                          |
| 4   | Выполнить ходы и реакции против каждой враждебной стороны, попробовать чужого бойца                                   | Общий прогноз/правила, права проверены, чужая команда отклонена           |
| 5   | Вывести одну сторону, продолжить оставшиеся две, завершить бой                                                        | Правильный итог, очередь и сохранённая история выбывшей стороны           |
| 6   | Повторить одинаковые setup/seed/команды, воспроизвести старый replay                                                  | Детерминированный новый результат и совместимость старой редакции         |

Принятые проверки — MULTI-1–MULTI-8 у владельца кампании.
Партию, её право управления и capability сессии связывает авторизованный адаптер.

## 4. Обычная компания и кампанийный путь

Выделенный локальный стенд настраивается по
[LOCAL_DEVELOPMENT](../../docs/engineering/LOCAL_DEVELOPMENT.md#environment-contract).
Для нового стенда подготовить .env из примера с его собственными именами
ресурсов, портами и источником данных. Существующая конфигурация выбирается
по T001 вместе с её владельцем.

На подготовленном собственном стенде команды запуска следующие.

```bash
pnpm db:up
pnpm db:migrate:up
pnpm dev
```

При стандартных локальных портах приложение доступно на `http://127.0.0.1:5173`.
Аккаунты и способы входа описаны в локальном runbook. Для двух компаний
использовать разные профили браузера. Фактические порты и company IDs записать.

Готовность стандартного API проверяется отдельно от живости процесса.

```bash
curl --fail --silent --show-error http://127.0.0.1:3000/health/live
curl --silent --show-error --write-out '\n%{http_code}\n' http://127.0.0.1:3000/health/ready
```

При доступных обязательных зависимостях readiness возвращает 200.
На выделенном стенде проверить также 503 при недоступности его обязательной
базы, затем восстановить доступность и повторить обычный вход по N12.

| Путь       | Обычные действия                                                                               | Проверяемый результат / владелец                                                                                                 |
| ---------- | ---------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| Контракт   | Вход → принятое дело → цель → помощник по допуску → доказательство → заказчик → повторный вход | Одна полная выплата, трофей по политике, действительное участие и следующий шаг. N02                                             |
| Подготовка | Услуга/замена, припасы, продажа, обязательство умершему                                        | Законный поставщик/получатель, точные расходы, владение и сохранённое состояние. N03/N04/N06, loot sale                          |
| Обучение   | Курс, завершение/остановка/прерывание, переобучение, согласие/отказ от прозвища                | Прогресс и расчёт сохранены, старый навык действует до принятого завершения, поступок подлинный. N06                             |
| Мир        | Маршрут → остановка → новый путь → место → повторный вход двумя наблюдателями                  | Положение и сроки, собственное знание, даты маркеров и местный доступ. N07                                                       |
| Бой        | Физическое прибытие/допуск, действия S4, сдача/отход/недееспособность, итог                    | Собственные бойцы, сохранённое имущество, допустимое освобождение и продолжение компании. N08                                    |
| Контент    | 20 квестов, обе ветви четырёх моральных выборов, B4                                            | Личные находки, один общий исход, реальные потребители последствий и выплата B4 40 крон из проверенных средств. N05/M1-QUESTS/B4 |

B4 следует T033 → T034, обучение — T018 → T019 → T020.

## 5. Реальная сохранность и сбои

Для R1–R5 использовать отдельную одноразовую PostgreSQL-базу с подтверждённым
владением. Переменная WARWRIT_QA_DATABASE_URL обозначает этот ресурс.
Интеграционные тесты используют существующие миграции, создают свои строки,
очищают их по принадлежности и закрывают соединения. Полный жизненный цикл
базы принадлежит исполнителю T029.

```bash
DATABASE_URL="${WARWRIT_QA_DATABASE_URL:?}" pnpm db:migrate:up
WARWRIT_COMPANY_DATABASE_URL="${WARWRIT_QA_DATABASE_URL:?}" pnpm exec vitest run apps/server/src/company/executor.integration.test.ts
WARWRIT_COMPANY_DATABASE_URL="${WARWRIT_QA_DATABASE_URL:?}" pnpm exec vitest run apps/server/src/company/routes.integration.test.ts
WARWRIT_FIRST_HUNT_ISOLATED_DATABASE_URL="${WARWRIT_QA_DATABASE_URL:?}" pnpm exec vitest run apps/server/src/contracts/company-transition.integration.test.ts
WARWRIT_ENCOUNTER_DATABASE_URL="${WARWRIT_QA_DATABASE_URL:?}" pnpm exec vitest run apps/server/src/encounters/postgres.integration.test.ts
```

Опциональная DB-переменная включает реальное выполнение соответствующих тестов.
SKIPPED записывается как NOT_RUN. Подтвердить R1/R2 при сбое до commit и потере
ответа после него, R3 при конкуренции и изменённом повторе, R4 при exact retry
после поздних изменений. Сначала проверяется право на private readback.
Факт прохождения старой проверки связывается с её конкретным покрытием.
Для R2 отдельно вызвать сбой между сохранением исхода боя и применением
последствий. После перезапуска проверить сохранённое ожидание обработки,
возобновление с однократным применением последствий и предусмотренный выбор лидерства. Освобождение
компаний проверяется вместе с атомарно применёнными последствиями.

R5 использует согласованный архив и отдельную пустую цель восстановления.
Другой исполнитель по подготовленной инструкции выполняет восстановление,
обычный вход и продолжение компании. Его результат вместе с локальным
запуском по T030 подтверждает SC-008.
PostgreSQL-клиент версии 17 и параметры собственных ресурсов подготовлены заранее.
WARWRIT_QA_SOURCE_DATABASE_URL и WARWRIT_QA_RESTORE_DATABASE_URL указывают
на разные выделенные ресурсы. Файл архива хранится вне публикуемых артефактов.

```bash
pg_dump --format=custom --file="${WARWRIT_QA_BACKUP_FILE:?}" "${WARWRIT_QA_SOURCE_DATABASE_URL:?}"
pg_restore --exit-on-error --single-transaction --dbname="${WARWRIT_QA_RESTORE_DATABASE_URL:?}" "${WARWRIT_QA_BACKUP_FILE:?}"
```

Сервер восстановленной копии получает её собственные DB/origin/порты и изоляцию
от интеграций исходного мира по N11. Проверить обычный вход и следующее законное
действие, состояние людей, денег, предметов, обучения, знания, пути/боя и квитанций.
Зафиксировать совместимые schema/content/ruleset versions, время восстановления
и ресурс источника/цели. Сохранённый источник остаётся владельцем своей истории.

## 6. Desktop, производительность и завершение

Пройти карту → место → бой → результат → карту и повторный вход на фактическом
целевом устройстве. Проверить день/ночь, максимальный состав и повторные открытия.
Записать build, viewport/DPR/zoom, устройство, метод, время кадра/FPS, загрузку,
память и ресурсы сцены. При изменении повторить ту же нагрузку для сравнения.
N10 определяет принятие численного бюджета и целевой статус проверки.

T036 сводит SC-001–SC-009 на совместимой версии с ответом владельца.
T037 записывает результат у владельца задачи, короткий CHANGELOG и достигнутый
checkbox roadmap. История доказательства включает путь, выбранный исход,
сохранённые последствия, команды/результаты, ограничения и следующий шаг.
Merge, размещение и платные ресурсы следуют разрешениям AGENTS.md.
